## 1. Customer's current booking-create payload

Source: `dojo-walk-customer/lib/features/booking/screens/booking_confirmation_screen.dart` on `main`.

The Customer writes to `bookings/{autoGeneratedDocumentId}` and calls `bookingRef.set(bookingData)`. The base payload currently includes:

- `bookingId` (same value as document ID)
- `customerId` (Firebase Auth UID)
- `walkType` = `scheduled`
- `bookingPlan` = `one_time | regular | customize`
- `serviceType` = `temporary_walk | regular_walk | custom_walk`
- `serviceName`, `petName`, `dogId`, `petDetails`
- `pickupAddressId`, `pickupAddress`
- `scheduledAt` (Timestamp)
- `duration` (currently a string such as `30 minutes`)
- `preferredTime` (string; immediate flow can use `ASAP`)
- `walkCount`, `walkSchedules`
- `status` = `pending`
- `walkerId` = `null`
- `cancelRequest` = `null`
- `createdAt` = server timestamp

Conditional fields:
- Regular: `frequency=daily`, `walksPerWeek=7`, `walksPerDay`, `planStatus=pending_confirmation`, `dailyWalkTemplate`.
- Choose Dates: `walksPerDay`, `selectedDates` (list of YYYY-MM-DD strings), `dateSchedules` (dates as Timestamps with walk lists).

**Security implication:** A rules schema that only whitelists a small generic booking object will reject valid current customer bookings. Conversely, blindly allowing arbitrary maps such as `petDetails` and `pickupAddress` is too permissive. Define nested key/type validation and validate pet/address ownership before finalizing create rules.

## 2. Customer-owned pet validation

Before writing, Customer reads:
`users/{auth.uid}/pets/{dogId}`.

The client checks that the pet exists and then embeds a snapshot in `petDetails`. Firestore Rules for the booking write should not trust the embedded snapshot alone. Validate that `dogId` refers to an existing pet under the authenticated customer's user document, and restrict which pet fields can be copied. Apply the same ownership principle to the selected pickup address, after confirming the real address document path and ID conventions.

## 3. Status vocabulary currently in code

Customer booking screen recognizes these status values:
- `pending`
- `finding_walker`
- `walker_assigned`
- `walker_arriving`
- `confirmed`
- `assigned`
- `accepted`
- `in_progress` and `in progress`
- `completed`
- `cancelled` and `canceled`

Admin booking screen filter labels are human-readable:
- `Pending`
- `Walker Assigned`
- `Walker Accepted`
- `Walk In Progress`
- `Completed`
- `Cancelled`

Admin currently compares each stored status against the selected label after lowercasing; spaces and underscores are not normalized. Thus e.g. `walker_assigned` will not match `Walker Assigned` as a filter. The Admin screen reads `bookings` and filters/sorts client-side in the inspected source.

**Recommendation:** Define one canonical machine status enum (lowercase snake_case) and a shared UI-label mapping. Do not store translated/display labels as status values. Document permitted transitions separately for Customer, Walker, and Admin.

## 4. Partner rules findings

Source: `dojo-partner/firestore.rules` on `main`.

- `isAdmin()` currently requires an existing `admin_users/{uid}` record with `isActive == true` and `role == 'super_admin'`.
- Booking reads are allowed to Admin, matching `customerId`, or matching `walkerId`.
- Booking `create` is explicitly denied (`allow create: if false`) in the inspected file.
- Customer booking updates are restricted to changes in `cancelRequest` and `updatedAt`, while status must already be one of `pending`, `confirmed`, or `assigned`.
- Walker booking updates are restricted to changes in `status`, `updatedAt`, `walkSchedules`, `walkNotes`, `peeCount`, `poopCount`, `distance`, and `durationActual`, with existing `walkerId` matching the caller.
- Admin updates are allowed by a separate rule.

Firestore combines matching `allow` statements with OR semantics; each rule block must be evaluated together with all overlapping matches and the final catch-all. These are source-file findings only, not proof of active Production rules.

## 5. Potential compatibility risks to resolve

1. **Booking creation:** Current inspected Partner rules deny all client booking creates. If these are the active shared rules, Customer booking creation will fail. Active Production rules are unverified.
2. **Status mismatch:** Customer machine statuses and Admin display-label filters are not aligned.
3. **Schedule representation:** `scheduledAt` is a Timestamp; Partner Home was previously observed filtering today's bookings by a `date` field. Confirm exact Partner query path and migrate it to a single documented scheduling field/strategy.
4. **Duration type:** Booking root `duration` is a string while nested schedule duration is numeric.
5. **Date schedules:** Selected-date bookings store `selectedDates` and `dateSchedules` in addition to the primary `scheduledAt`; rules must validate the nested lists and cap their sizes.
6. **Pet/address integrity:** Customer embeds data maps; the final rules need ownership checks and allowed nested keys.
7. **Walker assignment:** The inspected Admin booking list is read/filter UI; it does not establish a complete assignment workflow. Locate and audit any assignment service/action before designing admin transitions.
