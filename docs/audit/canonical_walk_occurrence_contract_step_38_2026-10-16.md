# DOJO WALK — Canonical Walk Occurrence Contract
## Step 38 • 2026-10-16

**Status:** Proposed design / documentation only  
**Scope:** Customer, Partner, Admin, Firebase data contract  
**Branch:** `audit/zone-service-area-mapping-2026-10-16`

## 1. Purpose

Each real scheduled dog walk must have one stable identity shared across Customer booking schedules, Partner assignment/live-walk records, and Admin operations. A parent booking can contain multiple walks, so `bookingId`, list index, `walkNumber`, or formatted time alone is not a safe occurrence identity.

## 2. Proposed canonical occurrence record

Suggested logical record: `walk_occurrences/{occurrenceId}`. This is a proposal, not a claim that this collection currently exists.

Required fields:
- `occurrenceId`: immutable ID generated by a trusted backend.
- `bookingId`: parent customer booking.
- `customerId`: booking owner.
- `walkerId`: currently assigned walker UID; null while unassigned.
- `assignmentVersion`: incremented whenever assignment changes, to invalidate stale responses.
- `serviceDate`: date string `YYYY-MM-DD` interpreted in `Asia/Kolkata`.
- `scheduledStartAt`, `scheduledEndAt`: authoritative timestamps, not display-only time strings.
- `status`: normalized lifecycle state.
- `confirmation`: phase, response status, reason code/text, response time and deadline.
- `createdAt`, `updatedAt`, `schemaVersion`.

Suggested lifecycle states: `pending_assignment`, `assigned`, `accepted`, `in_progress`, `completed`, `cancelled`, `reassignment_required`. Existing app statuses must be mapped deliberately before adoption; do not silently rename live production values.

Suggested confirmation structure:
```json
{
  "phase": "pre_start",
  "status": "pending",
  "reasonCode": null,
  "reasonText": null,
  "respondedAt": null,
  "responseBy": null
}
```
Allowed phase values: `pre_start`, `post_completion`. Allowed response states: `pending`, `confirmed`, `reason_submitted`, `expired`. Expiry timing and exact transition policy remain product decisions.

## 3. Schedule materialization

Customer schedule payloads are booking input/template data. A trusted backend should materialize one occurrence for each actual walk:
- one-time ASAP: one occurrence with a server-authoritative start policy;
- one-time scheduled: one occurrence;
- regular plan: one occurrence per scheduled walk instance/date, not one ID for the whole recurring plan;
- customize plan: one occurrence per selected date and walk.

Occurrence IDs must not depend on mutable array order, formatted time, `walkNumber`, or parent `bookingId` alone. Preserve the source schedule fields needed for audit and support changes through explicit, validated updates.

## 4. Popup targeting and timing

A popup/notification may be delivered only when the backend rechecks all conditions:
1. the occurrence exists and has the intended phase;
2. the recipient UID matches the current `walkerId`;
3. the assignment version still matches;
4. the walker is approved, verified, active, and not suspended or on approved leave for the relevant time;
5. the occurrence is eligible for the relevant pre-start or post-completion action;
6. no live walk is in progress for that occurrence/walker.

No fixed global clock times. Trigger timing from the occurrence's actual scheduled timestamps and lifecycle events. Never show the pre-start popup during a live walk. Post-completion confirmation is only eligible after authoritative completion. If reassignment happens, invalidate the previous walker's pending prompt and reject stale responses.

A client-side filter alone is insufficient; trusted backend logic and Firestore Rules must enforce authorization and valid transitions.

## 5. Reason response

Selecting “Reason” must require both a recognized `reasonCode` and descriptive text when required by policy. `OTHER` must require non-empty explanation text. A reason submission is not equivalent to confirmation. Missing response remains pending until an explicitly approved expiry/escalation policy changes it.

## 6. Leave, suspension and reassignment

The Step 37 audit did not identify an authoritative Leave date/range contract or a dedicated reassignment workflow in the inspected Admin files. Do not assume those fields exist. Define and approve the Leave schema separately before enforcing it.

Do not silently cancel or discard an already accepted assignment if the walker later becomes unavailable. Mark it for explicit Admin reassignment/escalation, preserve the audit trail, and increment assignment version when reassigned.

## 7. Leave schema decision is still open

Step 32 previously suggested `walkers/{walkerUid}/availability/{YYYY-MM-DD}`, but that path was a proposal and was not verified as implemented. Confirm a single canonical availability/leave model before writing production logic.

## 8. Security and integrity requirements

- Only trusted backend code may create canonical occurrences and change authoritative assignment/lifecycle fields.
- A walker may respond only to an occurrence currently assigned to their authenticated UID.
- Validate `occurrenceId`, phase, assignment version, reason fields, and legal state transitions server-side and in Rules where feasible.
- Make responses idempotent; duplicate requests must not create duplicate incidents or overwrite a newer assignment's response.
- Keep Admin actions and reassignment auditable.
- Do not rely on hidden UI controls as authorization.
